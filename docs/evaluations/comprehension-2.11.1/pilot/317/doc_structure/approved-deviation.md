# Coordinator-approved cost deviation (verbatim)

The protocol's limits of at most 32 LLM calls per candidate, 600 seconds total, 512 output tokens per interpretation and 768 per grade stay in force unchanged (so plan 4 cases x 4 conditions = 16 interpretation + 16 grading calls; for candidates with a different number of conditions choose the case count that fits 32 calls; #319 keeps its separate 40 calls/900 seconds). The 'reported total usage ceiling 32,768 tokens' was written for in-session subagents and is infeasible with the Codex CLI, whose fixed per-call input overhead you measured at about 15.1k tokens independent of the task. For this run the ceiling applies to CONTENT tokens: per call, content = reported input tokens minus the fixed overhead baseline (measure the baseline once per session as the input-token count of a minimal one-word prompt under the same flags, and record it) plus output tokens; ceiling 32,768 content tokens per candidate. Record both the raw reported usage and the content-token figure for every call. The owner authorised running these evaluations through the Codex subscription; this deviation changes a cost limit only and no accuracy criterion. All other protocol rules stand: unknown failed-call usage stops further automated calls for that candidate; missing/failed/ungraded jobs are not successes; a budget-exhausted run is 'hold / incomplete'. With 4 cases per candidate the sample is very small ? say so in every summary and do not present differences of one case as an effect. If a cheaper-overhead invocation exists (flags that drop built-in tool definitions or base instructions from codex exec), you may use it, as long as isolation and the zero-tool-event filter still hold.
